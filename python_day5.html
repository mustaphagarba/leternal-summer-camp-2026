🧱 Classes: Blueprints for Objects

A class is a blueprint. An object is a real thing built from that blueprint.

🏠 The blueprint for a house isn't a house — it's the PLAN.

Build from the plan, and you get a real house (an object)!

🎮 In our game: Player is the blueprint. Your actual curator on screen is the object.

📝 Defining Our First Class

class Player: def __init__(self, x, y): self.x = x self.y = y self.speed = 5
  • __init__ runs automatically when we create a Player
  • self means "this specific player"
  • self.x stores x ON this player, forever

🏗️ Creating a Player Object

class Player: def __init__(self, x, y): self.x = x self.y = y curator = Player(380, 550) print(curator.x) print(curator.y)
380
550
✨ curator.x reads like English: "the curator's x." That's the power of self!

⚙️ Methods: Functions That Live Inside a Class

class Player: def __init__(self, x, y): self.x = x self.y = y def move_left(self): self.x -= 5 def move_right(self): self.x += 5 curator = Player(380, 550) curator.move_right() print(curator.x)
385
🎯 A method is just a function that belongs to the class — it can use and change self's own data!

🎨 A draw() Method

class Player: def __init__(self, x, y): self.x = x self.y = y def draw(self, screen): pygame.draw.rect( screen, (255, 215, 0), (self.x, self.y, 40, 40) )
🖌️ Now drawing the curator is just curator.draw(screen) — the class hides all the messy details!

🧠 Why Bother With Classes?

  • All the curator's data lives in ONE tidy place
  • We can easily make MORE than one (great for enemies tomorrow!)
  • Code reads like English: curator.move_left()
👾 Tomorrow we'll create 8 Alien objects from ONE Alien class. Classes are what make that possible!

🗂️ Splitting Code Into Files

One giant file gets messy fast. Real projects split code into files by job.

📄 player.py → everything about the Player

📄 main.py → the game loop that USES Player

📄 File 1: player.py

player.py
import pygame class Player: def __init__(self, x, y): self.x = x self.y = y self.speed = 5 def draw(self, screen): pygame.draw.rect( screen, (255, 215, 0), (self.x, self.y, 40, 40) )

📄 File 2: main.py

main.py
import pygame from player import Player pygame.init() screen = pygame.display.set_mode((800, 600)) curator = Player(380, 550) running = True while running: ... curator.draw(screen) pygame.display.flip()
🔌 from player import Player pulls our class from the other file. Same folder, one import line!

🐛 Import Trouble?

  • Both files must be in the SAME folder
  • The filename is player.py → we write from player import Player
  • Capitalization matters! Player ≠ player
🕵️ "ModuleNotFoundError" almost always means a typo in the filename or import line.

🔫 Shooting: Bullets Are a List

A bullet is just a position that moves upward every frame.

bullets = [] # start with none on screen
🎯 We already know lists AND loops from Day 3 — shooting is just applying them to a new problem!

🔥 Firing on Spacebar

if keys[pygame.K_SPACE]: new_bullet = [curator.x + 18, curator.y] bullets.append(new_bullet)
➕ Every spacebar tap adds ONE more [x, y] pair to our bullets list!

⬆️ Moving Every Bullet

for bullet in bullets: bullet[1] -= 8 # move up the screen for bullet in bullets: pygame.draw.rect( screen, (255, 255, 0), (bullet[0], bullet[1], 4, 12) )
🔄 One loop moves ALL bullets. Another loop draws ALL bullets. Same pattern as the class register!

🗑️ Cleaning Up Off-Screen Bullets

bullets = [b for b in bullets if b[1] > 0]

This keeps only the bullets still ABOVE the bottom of the screen.

🧹 Without this, thousands of invisible bullets would pile up and slow the game down!
